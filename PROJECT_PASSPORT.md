# ФОРПОСТ - паспорт проекта

Дата актуализации: 25.09.2026. Этот документ описывает фактический локальный
стенд. Он не выдаёт локальную демонстрацию за промышленную информационную
систему и не раскрывает содержимое `data/raw`.

## Назначение и текущий результат

ФОРПОСТ - веб-сервис ситуационного центра для диспетчерской работы с
обезличенными наблюдениями СМВУ, их временной динамикой и прогнозом риска
прекращения телеметрии на следующие 24 часа. Реализован единый локальный
контур: данные -> подготовка снимка -> ML-релиз -> FastAPI -> Next.js UI.

В обзоре отображаются **реальные обезличенные записи локального снимка**:
журнальные ID, время, канал, значение и отметка о сработке. Они не являются
прогнозами. Реальными в схеме объектов являются доступные ID и связи иерархии;
координаты SVG намеренно условные и не являются картой Москвы.

## Как пользоваться стендом

1. Откройте `/` - «Обзор». Это фактическая оперативная сводка выбранного
   временного окна: KPI, графики и журнал.
2. В нижней временной шкале выберите «День», «Неделя» или «Месяц», перетащите
   ползунок либо используйте кнопки +/- 30 минут. Обзор и журналы меняются
   вместе с выбранным моментом; маркеры под шкалой ведут к отмеченным событиям.
3. Откройте `/sensor-failure`. Здесь показан опубликованный `v10`-релиз
   proxy-модели, его фактические validation/test-метрики, 24-часовой горизонт
   и прогнозы по каналам. Proxy означает риск тишины телеметрии, а не
   подтверждённую физическую поломку.
4. Откройте `/notifications` для сквозного сценария: прогноз -> факторы и
   наблюдения -> решение диспетчера -> локальный `simulated` черновик заявки.
   Для действий войдите в demo-сессию ОДС; она живёт 5 минут.
5. `/journals` - подробный журнал наблюдений, поиск, фильтры, карточка и
   human-only решение. Исходное наблюдение не изменяется.
6. `/topology` - структурная схема: колесо/кнопки меняют масштаб,
   перетаскивание перемещает схему, «Сбросить» возвращает исходный вид.
7. `/design-system` - локальные настройки интерфейса: стартовый диапазон,
   маркеры шкалы и плотность таблиц. Они хранятся только в браузере и не
   меняют ML-релиз, источники и права доступа.

## ML: фактическое состояние

Единственная обученная задача - `sensor_failure`: вероятность неожиданного
прекращения телеметрии в следующие 24 часа. Релиз `v10` использует CatBoost с
sigmoid-калибровкой, point-in-time признаки, temporal split, отдельную
калибровку, rolling validation и финальный отложенный test.

| Метрика | Validation | Final test |
| --- | ---: | ---: |
| Precision | 0.585 | 0.608 |
| Recall | 0.816 | 0.826 |
| F1 | 0.680 | 0.700 |
| PR-AUC | 0.632 | 0.797 |
| ROC-AUC | 0.831 | 0.918 |
| Brier score | 0.152 | 0.109 |
| ECE | 0.091 | 0.069 |

Рабочий порог - `0.18846`. В текущем локальном профиле числовые пороги
качества advisory: релиз помечен `limited`, а не «идеальный» или
«сертифицированный». Значения не подменяются. Артефакты расположены локально
в `ml/models/sensor_failure/v10/` и проверяются SHA-256 manifest перед выдачей
через API.

Пожарный риск, несанкционированный доступ и износ инфраструктуры не имеют
обученных моделей, поскольку в имеющемся snapshot отсутствуют необходимые
связанные источники и целевые исходы:

| Направление | Чего не хватает для честной модели |
| --- | --- |
| Пожар | Связка температура/дым, огневые работы, подтверждённые исходы пожара |
| Доступ | Журналы СКУД, допуски, результаты расследований |
| Износ | Реестр оборудования, даты ввода, ТО/ремонты/замены и устойчивые ID |

Интерфейс не генерирует для этих задач фиктивные вероятности.

## Архитектура и стек

```text
data/raw (локально, вне Git)
  -> Python connectors + build_local_snapshot.py
  -> data/processed/local-situation.json
  -> FastAPI / защищённые ML-артефакты
  -> Next.js BFF
  -> React-диспетчерский интерфейс
```

- Frontend: Next.js 15 App Router, React 19, TypeScript strict, Tailwind CSS,
  ECharts, Framer Motion, Zustand, date-fns, Lucide.
- API: FastAPI, Pydantic, Uvicorn, SlowAPI.
- Данные и ML: Python 3.12, pandas, NumPy, scikit-learn, CatBoost, LightGBM,
  skops, openpyxl, PyYAML.
- Локальные demo-операции: SQLite. PostgreSQL предусмотрен ТЗ, но не подключён.

## Реализованная безопасность

- Данные `data/raw` и производные локальные данные не попадают в Git.
- Локальные Git hooks, CI-проверки и шаблон server-side pre-receive защищают
  от случайной публикации выгрузок.
- API привязан к loopback; launcher запускает Next.js на `127.0.0.1:3000` и
  FastAPI на `127.0.0.1:8000` с временным service-token.
- BFF валидирует фиксированные пути, backend origin и JSON-контракты.
- Demo-операции защищены короткой signed-сессией, HttpOnly/SameSite cookie,
  canonical loopback Origin/Host-проверкой, CSRF и Idempotency-Key.
- FastAPI использует Bearer, RBAC/ABAC, rate limiting, ограничение тела,
  security headers, строгие Pydantic-схемы, проверку путей и SHA-256 ML-артефактов.
- Решения и черновики фиксируются в локальном hash-chain audit ledger.
- Последние проверки: TypeScript typecheck, ESLint, Ruff и Bandit пройдены;
  Semgrep не дал findings. Полный security audit выявил и после этого были
  исправлены DNS-rebinding для demo-сессии и анонимная выдача prediction feed.

### Kill chain и MITRE ATT&CK

Полная модель угроз находится в [`docs/THREAT_MODEL.md`](docs/THREAT_MODEL.md).
Она описывает сквозную kill chain: начальный доступ через зависимость/CI либо
секрет -> чтение или подмена локальной выгрузки -> data/label poisoning или
подмена model artifact -> ложный риск в UI -> ошибочное действие диспетчера и
попытка скрыть следы. Для каждого шага определены защитные барьеры и остаточный
риск.

| ATT&CK / риск | Реализованный контроль |
| --- | --- |
| T1195.001: компрометация зависимостей и dev tools | lockfile, hash-pinned Python lock, audits, Ruff, Bandit, Semgrep, TruffleHog |
| T1565.001: подмена данных, меток или ML-артефакта | schema validation, temporal split, manifests SHA-256, immutable versioned registry, Skops allowlist |
| T1499: отказ в обслуживании | chunked loading, лимиты файлов/body, Pydantic bounds, rate limiting, ограничение inference latency |
| T1552.001: секреты в файлах | `.env` ignore, scanning, short demo assertions, HttpOnly cookies, secret values не логируются |
| CWE-22 / T1005: path/symlink escape и чтение локальных данных | fixed roots, canonical paths, symlink rejection, allowlist task/version |
| T1041: утечка данных через Git/сеть | Git perimeter guards, loopback-only listener, `no-store`, UI не читает raw |

Остаточный риск честно зафиксирован: пока нет HSM/KMS-подписи publisher-а,
центрального secrets manager, корпоративного IdP/MFA, SIEM, TLS deployment,
backup/RTO и защищённой сегментации production-контура.

Ограничения: нет корпоративного IdP/MFA, TLS-termination, PostgreSQL,
центрального SIEM, подписей издателя ML-релизов, backup/RTO и LAN/Internet
deployment. Поэтому это защищённый локальный стенд, а не готовая КИИ-production
инсталляция.

## Сверка с ТЗ и оценка

В ТЗ действительно нет требования «все метрики должны быть выше 70%». Оно
оценивает качество кода, интегрируемость, скорость, достоверность расчётов и
прогнозов, рекомендации, настраиваемые параметры, объективность диаграмм, UX
и полноту документации. Числовых весов критериев ТЗ не задаёт, поэтому
математически честно назвать точное число баллов невозможно.

Сильные стороны для экспертизы: единый работающий сервис, реальные локальные
наблюдения, работающий ML-релиз с раздельными validation/test-метриками,
понятные ограничения, human-in-the-loop, интерактивный UI, документация,
воспроизводимые тесты и серьёзная защита данных/артефактов.

Наибольшие потери баллов: только одно из четырёх ML-направлений обучено;
отсутствуют реальные внешние интеграции ОДС/СКУД/АРМ-Контроль/ТО, погодный
источник, GIS-координаты, PostgreSQL, TLS/IdP/SIEM/backup и промышленная
эксплуатация. По качественным критериям текущий стенд может претендовать на
высокую оценку за техническую часть, но максимум без трёх источников и трёх
дополнительных моделей недостижим.

### Рабочий прогноз баллов

ТЗ не задаёт шкалу или веса, поэтому это не официальный расчёт. При типичной
100-балльной экспертизе разумный диапазон текущего стенда - **65-75/100**:

- **высокая оценка** за идею, стек, реальный локальный контур, UI, тесты,
  документацию, security architecture и одну работающую ML-задачу;
- **средняя оценка** за доказательность: есть отдельные validation/test
  метрики и прогнозы, но это proxy риска тишины телеметрии с quality status
  `limited`, а не подтверждённая физическая поломка;
- **неполученные баллы** за три отсутствующие ML-задачи, их источники,
  GIS, внешние read-only интеграции, PostgreSQL, LDAP/AD, TLS/SIEM/backup и
  production deployment.

При получении источников и закрытии трёх моделей/сквозных сценариев проект
может претендовать на 80+ по такой условной шкале; без них обещать максимум
было бы недостоверно.

## Приоритетные шаги для дополнительных баллов

1. Подключить read-only контракты ОДС, СКУД, АРМ-Контроль, реестр ТО/ППР и
   погодный API; сначала добавить schema/quality reports, затем модели.
2. Реализовать три недостающих модели на подтверждённых лейблах и показать
   прогноз -> факт по каждой задаче.
3. Подключить реальную GIS-геометрию объектов вместо условной SVG-компоновки.
4. Перенести demo-операции в PostgreSQL, интегрировать IdP/RBAC-группы,
   TLS, SIEM, мониторинг, backup и RTO-процедуры.
5. Подготовить презентацию на основе этого документа и `docs/DEMO_SCRIPT.md`.
