# Проект доказуемого ML-контура ФОРПОСТ

## 1. Цель

Создать рабочий локальный ML-релиз для прогноза потери телеметрии датчика,
который честно проходит требования ТЗ: горизонт не менее 24 часов,
`precision > 0.70`, `recall > 0.50` и batch inference менее пяти минут.
Одновременно реализовать проверяемую цепочку «прогноз → факт», безопасные
настройки, детерминированные рекомендации и готовые контракты трёх остальных
направлений без имитации отсутствующих данных.

## 2. Семантика задачи и границы утверждений

Основная задача называется «риск прекращения телеметрии в течение горизонта».
Она не называется физическим отказом датчика, пока отсутствует подтверждённая
связка с результатами выезда, ремонта или замены. Для 24, 48 и 72 часов
обучаются и версионируются отдельные релизы: изменение горизонта меняет
целевую переменную и не является простым UI-параметром.

Прогноз публикуется только из атомарного релиза, прошедшего все gates.
Anomaly/scenario результаты не содержат калиброванную вероятность аварии.
Сервис не принимает решение вместо диспетчера и не управляет оборудованием.

## 3. Данные и предотвращение утечки

Исходные файлы остаются в `data/raw` и никогда не попадают в Git, внешние
сервисы или логи. Dataset builder использует только записи с временем строго
раньше точки прогнозирования. Для каждого канала формируются независимые
временные срезы после достаточного окна прогрева.

Целевая метка равна единице, если после точки прогнозирования в заданном
горизонте не появляется ожидаемая телеметрия по согласованному proxy-правилу.
Версия стратегии метки фиксируется в model card. Изменение правила требует
новой версии схемы dataset и повторной оценки всех кандидатов.

Признаки включают:

- текущий возраст последнего наблюдения;
- медиану, MAD, квантили и коэффициент вариации межсобытийных интервалов;
- отношение текущего возраста к индивидуальному нормальному интервалу;
- изменение частоты относительно предыдущего окна;
- rolling count, alarm rate, missing/quality rate и статистики значения;
- линейный тренд и устойчивый тренд значения и интервалов;
- exponentially weighted mean/variance для частоты и значения;
- час, день недели, месяц и циклические `sin/cos`-признаки;
- тип датчика и инженерную систему;
- достаточность и усечённость истории.

Признак остаётся только если тест доказывает его причинность: изменение строки
после точки прогнозирования не должно менять рассчитанный в прошлом признак.

## 4. Разбиение и выбор модели

Временной порядок является обязательным. Самая новая часть данных один раз
фиксируется как final test и не используется для выбора признаков, модели,
гиперпараметров, калибровки или порога.

Предшествующая часть проходит rolling-origin backtesting минимум на трёх
последовательных validation folds. Между train, calibration, validation и test
действует embargo не короче соответствующего горизонта. В каждом fold должны
присутствовать оба класса и достаточное число положительных и отрицательных
примеров.

Кандидаты:

- Dummy prior как обязательный baseline;
- Logistic Regression;
- ExtraTrees;
- HistGradientBoosting;
- CatBoost;
- LightGBM;
- XGBoost только если он добавляет измеримое качество без ухудшения
  воспроизводимости и эксплуатационной стоимости.

Гиперпараметры оптимизируются только на rolling validation с ограниченным
детерминированным бюджетом. Предпочтение отдаётся более простой модели при
статистически неразличимом результате. Версии библиотек и seed фиксируются.

Калибровка `sigmoid` и `isotonic` обучается на отдельной поздней части train.
Рабочий threshold выбирается по validation при одновременном соблюдении
precision, recall и alert budget. Финальный test вычисляется ровно один раз
для замороженного champion и не запускает повторный поиск.

## 5. Quality gates и артефакты

Для публикации одновременно обязательны:

- `precision > 0.70`;
- `recall > 0.50`;
- `alert_rate` не выше выбранного безопасного бюджета и абсолютного потолка;
- PR-AUC лучше dummy baseline на установленную дельту;
- Brier score и expected calibration error не выше конфигурационных лимитов;
- inference менее 300 секунд;
- отсутствие temporal leakage и полный model card;
- совместимые schema/model/export и SHA-256 manifest.

Model card содержит метрики каждого rolling fold, агрегированные mean/min,
final test, confidence intervals, горизонт, threshold, alert budget, версии
схем и библиотек, временные границы, число строк частей и ограничения.
Отдельный evaluation report существует и при rejection, но не разрешает
serving и не содержит test-метрик после validation rejection.

## 6. Prediction outcome ledger

Backend поддерживает read-only журнал исторической оценки. Каждая запись
содержит идентификатор прогноза, версию модели, сущность, время прогноза,
горизонт, вероятность, threshold, ожидаемый исход, фактический исход после
созревания горизонта, confusion-класс и доступные объясняющие факторы.

Агрегаты рассчитываются сервером по выбранным фильтрам:

- TP, FP, FN, TN;
- Precision, Recall, F1, PR-AUC и ROC-AUC;
- Brier score и calibration bins;
- lift и precision@K для нескольких долей top-risk;
- alert rate;
- среднее и медианное заблаговременное предупреждение;
- bootstrap confidence intervals.

UI показывает отдельную страницу «Прогноз против факта» с фильтрами периода,
горизонта, версии модели, типа датчика и инженерной системы. Любой график имеет
табличную WCAG-альтернативу. Несозревшие прогнозы не считаются отрицательными.

## 7. Безопасные настройки

Настройки хранятся как версионированные локальные профили и проходят строгую
серверную схему. Диспетчер может выбрать только опубликованный релиз горизонта
24/48/72 часа, доступный sensor/system scope и один из режимов:

- высокая точность;
- сбалансированный;
- высокая полнота.

Режим выбирает заранее валидированный threshold из model card. Пользователь не
может вручную снизить порог так, чтобы нарушить минимальные gates. Alert budget
ограничен абсолютным потолком. Любое изменение профиля аудитируется, имеет
версию и может быть отменено новой записью без удаления истории.

## 8. Детерминированные рекомендации

Rule engine работает после валидированного прогноза и не изменяет probability.
Правило содержит уникальный ID и версию, необходимые признаки, условие,
последовательность действий, срок реакции, приоритет, источник и ограничения.

Рекомендация содержит:

- конкретные сработавшие условия и факторы;
- действия «проверить связь → проверить питание → назначить диагностику» в
  применимой комбинации;
- срок и приоритет;
- ссылку на правило;
- решение диспетчера, фактический результат и обратную связь.

До получения утверждённого текста РТЭК источник маркируется как внутреннее
правило ФОРПОСТ, а не нормативное требование заказчика. Отсутствие подходящего
правила даёт явное состояние «рекомендация не сформирована».

## 9. Остальные направления

Для `fire_risk`, `unauthorized_access` и `infrastructure_wear` вводится единый
capability contract: required sources/fields, evidence tier, readiness checks,
validation report и fail-closed состояние.

- Пожар: температура, дым, подтверждённый исход и контекст горячих работ.
- Доступ: СКУД, окно допуска и результат расследования.
- Износ: реестр оборудования, ТО, ремонт и замена с единым ID.
- Подтопление: насосные события и районные погодные данные через read-only
  адаптер с cache/timeout/rate limit и без передачи локальных идентификаторов.

При неполном источнике допускается только `anomaly` или `scenario` без
probability. Capability автоматически становится доступным лишь после
успешной проверки источника и валидированного артефакта.

## 10. API и UI

Новые read-only API:

- evaluation summary и folds;
- outcome ledger и агрегаты;
- calibration/lift bins;
- capability readiness.

Write API ограничиваются версионированными настройками, решением диспетчера и
обратной связью по рекомендации. Они требуют human identity, CSRF,
idempotency, RBAC/ABAC и audit chain. Service token остаётся read-only.

UI сохраняет строгий плоский Palantir-стиль и явно различает факт, proxy,
anomaly, scenario и simulation. Ни один unavailable/rejected результат не
заменяется нулём или синтетическим прогнозом.

## 11. Производительность и безопасность

Feature generation выполняется chunk-wise с ограниченным объёмом памяти.
Тяжёлое обучение остаётся офлайн. Serving загружает только проверенный bundle,
не исполняет pickle и не читает raw. Все файлы имеют size/path/symlink guards.

Новые зависимости допускаются после проверки лицензии, hash-pinned lock,
`pip-audit`, Bandit/Semgrep и воспроизводимого clean-room install. Никакие
телеметрические сервисы сторонних ML-библиотек не включаются.

## 12. Проверка и критерий завершения

Каждая функция реализуется test-first. Обязательны unit, temporal leakage,
rolling split, integration/API, schema, authorization, accessibility и
performance tests. Перед публикацией выполняются полный pytest/Vitest,
lint/typecheck/build, Ruff, Bandit, Semgrep, TruffleHog и dependency audits.

Работа считается успешно завершённой только если существует опубликованный
локальный релиз хотя бы для 24-часовой proxy-задачи, он проходит все quality
gates на untouched test, API отдаёт прогнозы, UI показывает прогнозы и
outcome-аналитику, а документация честно фиксирует доказательность и
ограничения. Если доступные данные объективно не позволяют пройти gates,
завершённым результатом является доказанный rejection с исчерпывающим
validation-анализом; gates и test при этом не подгоняются.
