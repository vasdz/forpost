# Политика безопасности локального контура

## Принципы

- Fail closed: отсутствующий IdP, снимок, model card или валидный ML-релиз не
  заменяется demo-данными и не даёт успешный бизнес-ответ.
- Least privilege: service subject только читает; решение по прогнозу требует
  идентифицированного человека и отдельного разрешения.
- Real data stays local: первичные данные, производные строки, модели, экспорты
  и метрики конкретной выгрузки не отправляются во внешние сервисы и CI.
- Evidence before presentation: `proxy`, `anomaly`, `scenario` и `validated`
  не взаимозаменяемы; интерфейс обязан показывать фактический tier.
- Defense in depth: схема, лимиты, auth, manifests, аудит и human-in-the-loop
  используются совместно.

## Поддерживаемая конфигурация

Локальный профиль поддерживает только listener `127.0.0.1` без reverse proxy,
проброса порта, LAN или публичного DNS. Исходные данные находятся в
`data/raw`, ограниченный UI-снимок — в `data/processed`, ML-релизы — в
`ml/models`; все три категории должны оставаться локальными и неотслеживаемыми
Git. Каталоги с данными и артефактами нельзя передавать внешнему сканеру.

Production требует отдельного threat model и как минимум TLS termination,
сетевой сегментации, корпоративного IdP/MFA, централизованного secrets manager,
неизменяемого SIEM-аудита, backup/restore, DLP и подписанного registry моделей.

## Аутентификация и решения

- API не доверяет `X-User`, `X-Role` и аналогичным клиентским заголовкам.
- Неверная/отсутствующая Bearer-схема получает `401`; отсутствие доверенного
  провайдера идентичности — `503`, а не анонимный доступ.
- Server-to-server субъект не может выполнять human-only write.
- BFF write-запросы требуют same-origin и совпадающий CSRF token; session
  assertion хранится в `HttpOnly`, `SameSite=Strict` cookie.
- Решение диспетчера относится только к существующему текущему прогнозу и
  записывается в audit ledger. Прогноз не выполняет действие автоматически.

## Данные и ML-артефакты

- HTTP-клиент не задаёт путь к исходному или модельному файлу.
- Canonical path проверки и запрет symlink не позволяют выйти из фиксированного
  локального корня обычным route-запросом.
- Релиз модели публикуется атомарно в новой неизменяемой версии `vN`.
- SHA-256 связывает `model.skops`, model card и prediction export; serving
  дополнительно проверяет task, version, feature schema, evidence tier,
  калибровку, test-метрики и allowlist типов Skops.
- Hash-файл в том же каталоге обеспечивает контроль целостности, но не
  аутентичность издателя. До production необходима внешняя подпись.

## Secure development lifecycle

Обязательный локальный gate перед передачей кода описан в
[LOCAL_VERIFY.md](LOCAL_VERIFY.md):

- ESLint/TypeScript strict, Vitest и production build;
- pytest, Ruff check/format и Bandit;
- локальный Semgrep с отключённой телеметрией;
- TruffleHog по явному allowlist путей, исключающему `data` и `ml/models`;
- `npm audit`, clean-room `pip-audit` и `pip check`;
- Git perimeter guard и проверка индексируемых путей.

Результаты конкретного прогона фиксируются отдельно в
[SECURITY_AUDIT.md](SECURITY_AUDIT.md). Прохождение сканеров не заменяет ручную
проверку границ доверия и не является обещанием отсутствия уязвимостей.

## Зависимости и supply chain

- npm устанавливается из lockfile командой `npm ci --ignore-scripts`;
- версии исправлений и принятые риски отражаются в
  [RISK_REGISTER.md](RISK_REGISTER.md);
- Python runtime проверяется в чистом окружении, а собственные editable-пакеты
  покрываются SAST и тестами;
- production-граф Python фиксируется в `requirements-prod.lock` с SHA-256
  хэшами; обновление выполняется только из `requirements-prod.in` с повторным
  тестированием и `pip-audit`;
- до промышленного развёртывания дополнительно нужны SBOM и доверенный
  внутренний proxy реестров;
- CI actions и container base images должны закрепляться immutable digest/SHA.

## Логи и аудит

В логи запрещено помещать содержимое строк, секреты, полные локальные пути и
сырой prediction payload. Допустимы тип события, обезличенный технический ID,
результат gate и счётчики. Локальная цепочка хэшей обнаруживает изменение
аудита, но не защищает от администратора машины; production обязан экспортировать
события во внешнее append-only хранилище.

## Реагирование

При подозрении на утечку или подмену:

1. остановить serving и обучение, сохранив исходные файлы для расследования;
2. отозвать затронутые секреты и заблокировать релиз модели;
3. проверить Git history, audit chain, manifests и источник данных;
4. не «исправлять» hash рядом с подозрительным файлом;
5. создать новую версию только после независимой проверки и зафиксировать
   причину инцидента.

Контакт и SLA реагирования определяет владелец защищённого контура; публичный
issue не должен содержать данные, секреты, пути или артефакты модели.
