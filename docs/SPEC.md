# Спецификация продукта: ситуационный центр АО «Москоллектор»

## 1. Дизайн-философия

Ситуационный центр сочетает эстетику Palantir Foundry и московский государственный стиль: серьёзный, ясный, инженерный интерфейс с монохромной основой, большим количеством свободного пространства и семантическим использованием цвета.

Интерфейс должен помогать оператору быстро отвечать на три вопроса: **что происходит, почему это важно и какое действие требуется**. Сложные связи между объектом, телеметрией, работами и прогнозом показываются в виде подписанных данных и временных последовательностей, а не декоративной графики.

Обязательные принципы:

- нейтральная рабочая поверхность и плоские панели с тонкой границей;
- один визуальный фокус на один блок: ключевой KPI, тревога или действие;
- цвет передаёт статус и тип данных, но не является единственным способом сообщить значение;
- все подписи, статусы и действия — на русском языке в официально-деловом стиле;
- интерфейс показывает только подтверждённые наблюдения из разрешённого источника; отсутствие источника всегда обозначается явно и не подменяется значением.

Запрещено:

- скругления больше `6px`;
- градиенты;
- пружинящие, бесконечные и декоративные анимации;
- декоративные иллюстрации и фоновые изображения;
- географические карты;
- цвет как единственный индикатор критичности;
- стеклянные панели, выраженные тени и визуальный шум.

## Текущий режим данных

Разделы 5–7 описывают целевую информационную архитектуру. В текущей фазе
разрешены только подтверждённые локальные наблюдения, каналы, негеографическая
иерархия объектов и результаты проверенного локального ML-релиза. Сейчас такой
релиз может существовать только для `sensor_failure` и обязан быть явно
маркирован как `proxy`: он оценивает прекращение телеметрии, а не подтверждает
физический отказ. Любая панель, для которой нет подтверждённого источника,
интеграции или допустимого релиза, показывает русскоязычное состояние
недоступности. Пожарный риск, несанкционированный доступ и износ инфраструктуры
остаются fail-closed. Ни одна панель не может подменять отсутствие данных
демонстрационными KPI, вероятностями, рекомендациями, заявками, пользователем
или уведомлениями. Это правило имеет приоритет над целевыми описаниями ниже.

## 2. Палитра

Цветовая система задаётся CSS-переменными. Тема определяется классом на корневом элементе: `.theme-dark` или `.theme-light`. Значения акцентов одинаковы в обеих темах.

```css
:root {
  --color-danger: #D9342B;
  --color-data: #00B8D4;
  --color-success: #10B981;
  --color-warning: #F59E0B;
}

.theme-dark {
  --color-bg: #0B0E11;
  --color-panel: #1A1D23;
  --color-panel-2: #252830;
  --color-border: #2E3138;
  --color-text: #FFFFFF;
  --color-text-muted: #A0A4AB;
}

.theme-light {
  --color-bg: #F5F5F7;
  --color-panel: #FFFFFF;
  --color-panel-2: #E8E8ED;
  --color-border: #D1D1D6;
  --color-text: #0B0E11;
  --color-text-muted: #6B7280;
}
```

| Токен | Значение и правило |
| --- | --- |
| `--color-danger` | `#D9342B`; только критичные тревоги, опасные действия и прогноз высокого риска. |
| `--color-data` | `#00B8D4`; история телеметрии, активный диапазон и нейтральные данные. |
| `--color-success` | `#10B981`; штатное состояние, успешно выполненные действия и подтверждённые связи. |
| `--color-warning` | `#F59E0B`; внимание, пороговый риск и незавершённая проверка. |

Любая цветовая метка сопровождается текстовым статусом, иконкой или значением. Для текста используется контраст не ниже `4.5:1`; для крупного текста — не ниже `3:1`.

## 3. Типографика

| Назначение | Семейство | Начертание | Правило |
| --- | --- | --- | --- |
| Заголовки | `Inter Tight`, fallback `Golos Text`, sans-serif | 600–700 | Название страницы, секции, KPI-заголовки. |
| Основной текст | `Inter`, fallback `Golos Text`, sans-serif | 400 | Пояснения, фильтры, таблицы, кнопки и статусы. |
| Телеметрия | `JetBrains Mono`, monospace | 500 | Только числовые значения телеметрии, ID, коды и timestamps. |

Шкала размеров: `32 / 24 / 20 / 16 / 14 / 12 / 11px`. Базовый вертикальный ритм — `8px`; все высоты строк, отступы и интервалы выстраиваются как кратные `4px`. Моноширинный шрифт не применяется к обычному тексту, названиям объектов и навигации.

## 4. Геометрия и движение

- Радиус компонентов — `4px` по умолчанию, `6px` только для модальных окон и крупных панелей.
- Границы — `1px solid var(--color-border)`; панели не используют тяжёлые тени.
- Spacing — только значения, кратные `4px`: `4, 8, 12, 16, 20, 24, 32, 40, 48px`.
- Анимации занимают `150–250ms` с easing `ease-out`.
- Анимация допускается только при изменении данных: появление новой тревоги, перестроение ряда, изменение KPI, открытие/закрытие панели или смена layout.
- При `prefers-reduced-motion: reduce` анимации отключаются или заменяются мгновенной сменой состояния.

## 5. Каркас интерфейса

### Header

Высота — `64px`. Header фиксирован в верхней части рабочей области и содержит:

1. breadcrumbs: текущий раздел и контекст объекта;
2. переключатель светлой/тёмной темы;
3. статус ML-модели: версия, состояние и время последнего расчёта;
4. центр уведомлений с числом непрочитанных тревог;
5. меню пользователя.

### Sidebar

Ширина развёрнутого состояния — `240px`; sidebar сворачиваемый. В свёрнутом состоянии остаются иконки с доступными tooltip и `aria-label`.

Порядок разделов:

1. Обзор;
2. Отказ датчика;
3. Пожарный риск;
4. Несанкционированный доступ;
5. Износ инфраструктуры;
6. Реестры;
7. Журналы;
8. Заявки;
9. Настройки.

Активный раздел отмечается фоном `--color-panel-2`, левой границей `--color-data` и текстовой подписью. Неактивный пункт не использует акцентный цвет.

### Рабочая область

Основная область использует 12-колоночную сетку с предсказуемыми полями. Верхняя строка каждой страницы содержит заголовок, краткое описание, глобальные фильтры страницы и отметку актуальности данных. Панели выравниваются по общей сетке; компоненты не выходят за границы контейнера.

### Footer: timeline playback

Внизу рабочей области закреплён footer высотой `80px` — **TIMELINE PLAYBACK**. Он содержит:

- переключатель диапазона: день / неделя / месяц;
- временной скраббер;
- маркеры критичных событий с текстовой расшифровкой в tooltip;
- кнопки Play/Pause и шага вперёд/назад;
- переключатель скорости `1x / 5x / 10x / 100x`;
- текущую дату и время в `JetBrains Mono`.

Скраббер обновляет все панели текущей страницы через глобальный Zustand-store. Панели получают единый выбранный момент и диапазон, а затем самостоятельно запрашивают/выбирают соответствующий срез данных через абстракцию источника данных. Playback не имеет автозапуска.

## 6. Спецификация страниц

### 6.1 Обзор

**Назначение:** дать диспетчеру сводную картину текущих рисков, состояния оборудования и ближайших действий.

**Панели и компоненты:**

- четыре KPI-карточки: активные прогнозы, критичные риски, оборудование под наблюдением, открытые заявки; каждая содержит значение, период, дельту и текстовый статус;
- график прогнозов по четырём типам с легендой и доступным табличным представлением данных;
- топ-10 рисков: приоритет, объект, тип прогноза, вероятность, горизонт и рекомендуемое действие;
- heat-матрица активности рисков за неделю;
- лента последних тревог с временем, источником, уровнем и статусом обработки;
- donut статусов оборудования с текстовой расшифровкой сегментов;
- мини-список заявок: номер, объект, приоритет, исполнитель и статус.

### 6.2 Отказ датчика

**Назначение:** выявлять деградирующие датчики, объяснять прогноз отказа и отличать сигнал от ложного срабатывания.

**Фильтры:** тип датчика, район, статус, уровень риска, горизонт прогноза.

**Панели и компоненты:**

- три KPI: датчики высокого риска, прогнозируемые отказы, доля ложных срабатываний;
- график «история → прогноз»: сплошная линия `#00B8D4` — история, вертикальная линия «Сейчас», пунктир `#D9342B` — прогноз, полупрозрачная confidence band, переключатель горизонта `7 / 14 / 30 дней`;
- Explainability-блок под графиком: probability в процентах, список факторов, вес каждого фактора в progress-bar и русское пояснение;
- рейтинг деградирующих датчиков: таблица с ID, типом, районом, probability, горизонтом, последней проверкой и sparkline за 24 часа;
- heat-матрица ложных срабатываний по времени и типу датчика.

### 6.3 Пожарный риск

**Назначение:** показывать риск пожара на основании температуры, задымления и корреляции с горячими работами АРМ-Контроль.

**Панели и компоненты:**

- четыре KPI: участки высокого риска, активные температурные отклонения, события задымления, работы с повышенным риском;
- два live-индикатора: температура и задымление, каждый со значением, порогом, статусом и sparkline;
- сигнальный баннер, видимый при probability пожара выше `70%`: объект, вероятность, горизонт, ключевой фактор и рекомендуемое действие;
- heat-матрица температурных событий;
- таблица корреляции с горячими работами АРМ-Контроль: заявка, организация, тип работ, период допуска, связанный участок, вероятность и статус проверки.

### 6.4 Несанкционированный доступ

**Назначение:** обнаруживать и расследовать аномальные паттерны доступа к объектам.

**Панели и компоненты:**

- четыре KPI: аномалии за период, критичные попытки, активные расследования, точки СКУД под наблюдением;
- лента аномальных карточек: время, точка СКУД, организация, тип события, уровень, текстовый статус и действие «Открыть расследование»;
- heat-матрица день × час;
- pie-диаграмма типов нарушений с легендой, количеством и долей;
- playback инцидента: последовательность события доступа, связанных допусков, действий диспетчера и итогового статуса. Текущий момент синхронизирован с глобальным footer playback.

### 6.5 Износ инфраструктуры

**Назначение:** приоритизировать обслуживание участков и объектов по состоянию, истории ремонтов и прогнозу износа.

**Панели и компоненты:**

- четыре KPI: участки критичного износа, средний индекс износа, ремонтные работы в плане, объекты с просроченным ТО;
- рейтинг участков по износу с индексом, трендом, возрастом, последним ремонтом и прогнозом;
- Gantt плановых ремонтов с периодами, статусом, исполнителем и фильтрами по району/типу объекта;
- модальное окно «Паспорт объекта»: возраст, износ в процентах, состав оборудования, timeline ремонтов, внешние факторы, прогноз, вероятность и кнопка «Создать заявку».

Модалка открывается по явному действию, блокирует взаимодействие с фоном, удерживает фокус и возвращает его на инициировавший элемент после закрытия.

### 6.6 Реестры

**Назначение:** обеспечивать поиск, проверку и экспорт первичных операционных данных.

**Табы:** Оборудование / Датчики / Журналы ОДС / АРМ-Контроль.

**Компоненты:**

- полнотекстовый поиск;
- фильтры по релевантным полям;
- сортировка и пагинация;
- экспорт текущей отфильтрованной выборки в CSV;
- модалка детального просмотра записи;
- отображение состояния загрузки, пустого результата и ошибки.

Статическая таблица использует нативную семантику `table`, `caption`, `thead`, `th` и `scope`. Интерактивная таблица применяет паттерн ARIA grid только когда нужны навигация стрелками, редактирование или выбор ячеек.

### 6.7 Заявки

**Назначение:** планировать и контролировать действия по прогнозам и подтверждённым инцидентам.

**Представления:**

- канбан по статусам: Новая / В работе / Ожидает подтверждения / Выполнена / Отменена;
- табличный вид с поиском, фильтрами, приоритетом, сроком, исполнителем и связанной сущностью.

Карточка заявки содержит номер, приоритет, объект, краткую формулировку, срок и ответственного. Переключение представлений не изменяет данные и сохраняет фильтры текущего пользователя.

## 7. Контракт прогноза

`GET /api/local-situation` передаёт только подтверждённые наблюдения и не
содержит прогнозов. `GET /api/predictions` отдельно читает локальные
версионированные ML-релизы. При отсутствии хотя бы одного допустимого релиза
маршрут отвечает `503 pending`; UI не восстанавливает последний ответ из
кеша и не генерирует замену. Успешный ответ дополнительно содержит
`available_types`: это список задач с валидным релизом, поэтому пустой список
алертов не смешивается с отсутствующей моделью.

```ts
type EvidenceTier = 'validated' | 'proxy' | 'anomaly' | 'scenario';

type PredictionType =
  | 'sensor_failure'
  | 'fire_risk'
  | 'unauthorized_access'
  | 'infrastructure_wear';

type Prediction = {
  id: string;
  entity_type: 'sensor' | 'location';
  entity_id: string;
  prediction_type: PredictionType;
  probability: number | null;
  anomaly_score: number | null;
  evidence_tier: EvidenceTier;
  calibrated: boolean;
  provenance: 'observed' | 'derived' | 'simulated';
  confidence: { lower: number; upper: number } | null;
  model_metrics: {
    precision: number;
    recall: number;
    f1: number;
    pr_auc: number;
    brier_score: number;
  } | null;
  quality_status: 'passed' | 'limited';
  limitations: string[];
  predicted_at: string;
  horizon_hours: number;
  model_version: string;
  factors: Array<{
    factor: string;
    weight: number;
    description: string;
  }>;
  recommended_action: string;
  priority: string;
  status: string;
};
```

Инварианты:

- `validated` и `proxy` содержат калиброванную `probability` от `0` до `1`,
  метрики модели и не содержат `anomaly_score`;
- `anomaly` содержит только score и не называется вероятностью; `scenario`
  имеет `simulated` provenance; эти уровни не отображаются как рабочий прогноз
  текущего диспетчерского интерфейса;
- текущий `sensor_failure` использует только `evidence_tier: proxy` и
  `label_strategy: cadence_adjusted_silence_horizon_proxy_v2`; он оценивает
  риск неожиданного прекращения ожидаемой телеметрии относительно
  индивидуального cadence, а физический отказ им не доказан;
- статус `passed` требует строго `precision > 0.70` и `recall > 0.50` на
  финальном temporal holdout; равенство порогу не считается прохождением;
- `predicted_at` передаётся в ISO 8601 с часовым поясом;
- `horizon_hours` — положительное целое число;
- `factors` упорядочены по абсолютному влиянию; для текущей модели это
  глобальная permutation importance, а не локальное причинное объяснение;
- `confidence: null` означает, что индивидуальный интервал не оценён; UI не
  строит синтетическую полосу неопределённости;
- `priority` и `status` отображаются через централизованный словарь русских подписей и статусов;
- компоненты не вычисляют прогноз; версия, evidence tier, calibrated flag и
  экспорт обязаны совпадать с model card;
- модель, model card и predictions публикуются атомарно, а API до разбора
  проверяет SHA-256 manifest. Ошибка схемы, пути, хэша или метрик исключает
  релиз из serving.

## 8. Доступность и стандарты

Ниже заданы целевые критерии WCAG 2.1 AA и ГОСТ Р 52872-2012. Формальное
подтверждение соответствия требует отдельного accessibility-аудита и испытаний
поддерживаемых браузеров; на текущем этапе оно не заявляется.

- Контраст обычного текста — не ниже `4.5:1`; для крупного текста — `3:1`.
- Вся функциональность доступна с клавиатуры; нет keyboard trap вне открытой модалки.
- Видимый focus-индикатор сохраняет контраст с фоном и не отключается через `outline: none` без доступной замены.
- У каждого интерактивного элемента есть понятное доступное имя; иконки без видимой подписи получают `aria-label`.
- Уведомления не опираются только на цвет: содержат текст уровня, иконку и timestamp.
- Графики предоставляют доступный заголовок, легенду, описание и альтернативное табличное представление данных.
- Модальные окна используют нативный `<dialog>` либо `role="dialog"`, `aria-modal="true"`, доступное имя, ловушку фокуса, Escape для закрытия и возврат фокуса инициатору.
- Таблицы имеют заголовки столбцов, понятную сортировку с `aria-sort`; интерактивные grid-таблицы поддерживают ожидаемую клавиатурную навигацию.
- Все тексты — на русском языке в официально-деловом стиле; дата и время локализованы для `ru-RU`.

## 9. Стратегия данных

### Сейчас: локальный снимок реальных обезличенных данных

Исходные и производные локальные файлы находятся только в игнорируемом Git-каталоге `data/`. Единственная точка поступления подтверждённых наблюдений в UI — `GET /api/local-situation`. Маршрут читает фиксированный локальный снимок, не принимает путь к файлу от клиента, не кеширует ответ и предназначен только для loopback-развёртывания.

В runtime запрещены импорты `/src/mocks`, генераторы, демонстрационные массивы и подстановка значений для недоступных источников. Экран показывает состояние недоступности, когда соответствующего подтверждённого источника или модели нет. Тестовые фикстуры изолированы от `data/` и не являются данными интерфейса.

### Потом: защищённый API

После утверждения интеграций локальный адаптер заменяется на защищённый API (FastAPI, Next.js Route Handlers или Supabase в согласованном контуре). Публичные типы домена, включая `Prediction`, и интерфейсы репозиториев остаются неизменными.

Компоненты получают данные только через выделенный клиентский слой. В компонентах запрещены прямые импорты тестовых массивов, SQL, вызовы Supabase и произвольные HTTP-запросы. Это позволяет заменить транспорт без изменения представлений и без появления неподтверждённых показателей.
