# Доступность ML-возможностей

## Правило публикации

Наличие страницы в интерфейсе не означает наличие модели. Вероятность
публикуется только из атомарного локального релиза, который прошёл проверку
схемы, доказательности, калибровки, temporal holdout, метрик и SHA-256.
Отсутствие или повреждение такого релиза даёт `503 pending`, а не нулевое,
синтетическое или ранее закешированное значение.

## Матрица текущего контура

| Задача | Доступные источники | Максимальная доказательность | Поведение сейчас |
| --- | --- | --- | --- |
| Отказ датчика (`sensor_failure`) | Локальные события и справочник каналов | `proxy` | Может быть локально обучена по `cadence_adjusted_silence_horizon_proxy_v2`. Результат означает риск неожиданного прекращения ожидаемой телеметрии в горизонте 24 часа относительно устойчивого индивидуального cadence, а не подтверждённую поломку. Публикуется только после строгого quality gate. |
| Пожарный риск (`fire_risk`) | Наблюдения есть; подтверждённых результатов проверки и полного контекста работ нет | Не выше `anomaly`, но не вероятность пожара | Production-прогноз fail-closed; страница сообщает о недоступности модели. |
| Несанкционированный доступ (`unauthorized_access`) | Нет согласованных журналов СКУД, допусков и верифицированных исходов | Не выше `anomaly`, но не вероятность нарушения | Production-прогноз fail-closed; страница сообщает о недоступности модели. |
| Износ инфраструктуры (`infrastructure_wear`) | Может быть доступна иерархия объектов; нет подтверждённой истории ТО/ремонтов | Не выше `scenario`, но не прогноз износа | Production-прогноз fail-closed; страница сообщает о недоступности модели. |

Уровни `anomaly` и `scenario` входят в транспортную схему для будущих
изолированных аналитических режимов. Они не имеют права содержать
калиброванную probability и не отображаются в текущем интерфейсе как рабочий
прогноз.

## Gate для proxy-релиза

Релиз `sensor_failure` создаётся только если:

- признаки построены строго из прошлого относительно каждой точки;
- fit, calibration, validation и test содержат оба класса и достаточное число
  примеров;
- между временными частями соблюдён purge не короче 24-часового горизонта;
- вероятность откалибрована на отдельном holdout;
- кандидат и три рабочих профиля прошли каждый rolling validation fold;
- модель и пороги заморожены до однократной оценки final test, несозревшие
  исходы исключены;
- на финальном temporal test одновременно выполнены `precision > 0.70`,
  `recall > 0.50`, alert rate `<= 0.35`, ECE `<= 0.20`, Brier score
  `<= 0.25` и улучшение PR-AUC относительно dummy baseline больше 0,01;
- batch inference занимает менее пяти минут;
- model card, модель и экспорт согласованы и опубликованы одной версией.

Факт прохождения порогов подтверждает только конкретный локальный релиз.
Репозиторий не содержит и не заявляет заранее достигнутых численных метрик.
Локальная команда воспроизведения: `.venv\Scripts\python.exe scripts/train_sensor_failure.py --version v4`.
Следующая изменённая попытка требует новой версии. Отказ на validation не
раскрывает test; отказ на test запрещает дальнейший подбор на этом holdout.
Отчёт не даёт права serving без проверенного модельного bundle.

## Что требуется для повышения доказательности

- Для отказа датчика: независимые записи проверки, ремонта, замены и причина
  прекращения телеметрии; после этого требуется новая стратегия лейбла и новая
  версия схемы признаков.
- Для пожара: верифицированные дымовые/температурные инциденты, результат
  проверки и согласованная связь с горячими работами.
- Для доступа: журналы СКУД, окна допусков и подтверждённые результаты
  расследований.
- Для износа: история ТО, ремонта и замены с временными метками и единым ID
  объекта.

Подключение источника само по себе не повышает evidence tier: сначала нужны
проверка качества, отсутствие утечки будущего, независимая оценка и
утверждённый human-in-the-loop процесс.
