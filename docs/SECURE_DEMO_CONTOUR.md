# Защищённый демонстрационный контур

## Статус и цель

Документ фиксирует утверждённый вариант A: работоспособный локальный контур
диспетчерского продукта при отсутствии доступов к корпоративным LDAP/AD,
help-desk, журналам ОДС и промышленной БД. Контур должен позволять показать
полный пользовательский процесс, но не выдавать симулированные сведения за
фактические данные АО «Москоллектор» или результаты ML-модели.

Решение использует реальные обезличенные журнальные наблюдения только из
локального каталога `data/raw`. Недоступные внешние взаимодействия заменяются
детерминированными адаптерами, включаемыми отдельным demo-режимом. Без этого
режима система сохраняет fail-closed поведение.

## Основания

Ответы постановщиков уточняют следующие правила:

1. Реальная интеграция с корпоративными LDAP/AD и Django help-desk на
   хакатоне невозможна; разрешена правдоподобная симуляция внешних API.
2. Ролевая модель включает районного диспетчера, центрального диспетчера ОДС,
   техника одного комплекса и администратора. Роли и группы областей видимости
   могут складываться.
3. В журнал должны попадать все тревожные события, а решение диспетчера не
   удаляет прогноз или событие из аналитики.
4. При отсутствии потокового подключения интерфейс должен обновляться без
   перезагрузки не реже одного раза в минуту.
5. Допустима условная схема коллекторов в GeoJSON. Для осей коллекторов
   достаточно `MultiLineString`; координаты должны быть явно обозначены как
   синтетические.
6. Технические значения датчиков нельзя безусловно удалять. Нетревожное
   техническое значение исключается из аналитических признаков, а тревожное
   сохраняется в оперативном журнале с признаком качества.
7. Массив 2021 года содержит эффект миграции системы мониторинга и по
   умолчанию не используется для обучения и оценки ML.
8. В текущей выгрузке отсутствуют подтверждённые решения диспетчеров, история
   ремонтов и записи АРМ-Контроль; такие сущности должны иметь явное
   происхождение `simulated` либо состояние `unavailable`.
9. Один пикет соответствует 10 метрам.

## Принципы достоверности

Каждая выдаваемая системой сущность получает `provenance`:

- `observed` — значение непосредственно прочитано из принятого локального
  источника;
- `derived` — значение воспроизводимо рассчитано только из `observed`-полей;
- `simulated` — значение создано demo-адаптером для отсутствующей внешней ИС;
- `unavailable` — требуемого источника или результата нет.

`simulated` не может преобразовываться в `observed`. Интерфейс показывает
происхождение рядом с карточкой, таблицей и экспортом. API включает
происхождение в каждый объект и не предоставляет режим, скрывающий маркировку.
ML-прогноз создаётся только из валидированного экспорта модели. Правила,
сценарные карточки и срабатывания датчиков не называются ML-прогнозами.

## Архитектура

### Компоненты

1. **Локальный адаптер СМВУ** потоково читает разрешённые CSV, проверяет
   ограничения размера и схемы, строит ограниченный снимок и показатели
   качества. Первичные файлы не покидают локальный контур.
2. **FastAPI** является владельцем оперативных бизнес-правил, идентичности,
   решений диспетчера, черновиков заявок, аудита и схемной топологии.
3. **Репозитории домена** отделяют бизнес-логику от хранения. Demo-реализация
   использует стандартный SQLite в `data/processed`; PostgreSQL-реализация
   подключается через тот же интерфейс без изменения UI и доменной модели.
4. **Next.js BFF** выдаёт браузеру только разрешённые поля, хранит серверные
   секреты вне клиентского bundle и проксирует запись с CSRF-защитой.
5. **Next.js UI** отображает данные, происхождение, свежесть и состояние
   интеграций. Он не вычисляет права, не создаёт диагноз и не принимает
   решение за диспетчера.

### Режимы запуска

`FORPOST_DEMO_MODE=0` является значением по умолчанию. Недоступная внешняя
интеграция возвращает контролируемый `503`, а write-операции без доверенной
личности запрещены.

`FORPOST_DEMO_MODE=1` разрешён только на loopback-интерфейсе. Для запуска нужны
отдельный секрет подписи сессий и ключ доступа, переданные через окружение.
Отсутствующий или короткий секрет останавливает demo-идентификацию. UI постоянно
показывает метку «Демонстрационный контур», а ответы симуляторов содержат
`provenance: "simulated"`.

## Контракт данных v2

### Канал

Публичная запись канала расширяется полем `objectId: string | null`.
Локальный загрузчик принимает две точные версии справочника:

- текущую схему без связи с объектом;
- обновлённую схему с единственным полем `ид_объект`.

При наличии поля каждый непустой `ид_объект` обязан ссылаться на объект из
справочника. При старой схеме `objectId` остаётся `null`; разбор текстового тега
не используется как скрытая подстановка связи.

### Событие

`eventId` источника не считается уникальным. Канонический идентификатор
оперативного события вычисляется как SHA-256 от версии источника, `eventId`,
`channelId` и `recordedAt`. Исходный ID сохраняется отдельно.

Событие содержит:

- исходное значение датчика;
- исходный тревожный признак;
- классификацию качества;
- допустимость для оперативного журнала;
- допустимость для аналитики и причину исключения;
- `provenance: "observed"`.

Технические значения `-3276`, `-127`, `-100`, `-255` и дата-артефакт эпохи
Unix классифицируются как `technical_anomaly`. Запись без тревожного признака
не передаётся в аналитические признаки. Запись с тревожным признаком остаётся
в оперативном журнале как `alarm_with_technical_value`. Список правил
версионируется и тестируется; исходное значение не перезаписывается.

### Политика периода 2021 года

Сырые события 2021 года остаются доступны для аудита истории. В наборах для
обучения, валидации и расчёта сравнительных трендов они по умолчанию получают
`analysisEligible: false` и причину `monitoring_system_migration`. Явное
включение допускается только отдельной версией ML-эксперимента и отражается в
его метаданных.

### Качество и свежесть

Публичный снимок содержит безопасный агрегат `dataQuality` без имён файлов,
путей, контрольных сумм и исходных записей:

- время построения снимка;
- время последнего наблюдения;
- число событий в публичном окне;
- число пропущенных временных меток;
- число технических аномалий в публичном окне;
- число каналов без подтверждённой связи с объектом;
- наличие обновлённой объектной связи;
- статус свежести `fresh`, `stale` или `historical`.

Порог `fresh` задаётся конфигурацией источника. Локальная историческая выгрузка
не должна отображаться как поток реального времени.

## Идентичность и доступ

### Роли

| Роль | Область видимости | Разрешённые действия |
| --- | --- | --- |
| Районный диспетчер | Назначенные районы и группы комплексов | Просмотр телеметрии и рисков, решение по тревоге, создание черновика заявки |
| Центральный диспетчер ОДС | Все районы и комплексы | Те же бизнес-действия во всём контуре |
| Техник | Один или несколько явно назначенных комплексов | Просмотр назначенных событий и черновиков, фиксация результата проверки |
| Администратор | Конфигурация ИС | Управление demo-профилями и просмотр аудита без права бизнес-решения |

Субъект содержит множество ролей и множество разрешённых областей. Полномочия
объединяются, области видимости объединяются. Центральная роль даёт глобальную
видимость. Административная роль сама по себе не добавляет бизнес-полномочий.
Любой доступ к объекту повторно проверяется на сервере.

### Demo-сессия

Demo-профили хранятся в серверной конфигурации без паролей и персональных
данных. После проверки ключа доступа BFF создаёт короткоживущую подписанную
сессию в `HttpOnly`, `Secure` в TLS-контуре и `SameSite=Strict` cookie. Для
изменяющих запросов проверяются Origin и CSRF-токен. Браузер не формирует роль,
район или ID пользователя заголовками.

BFF подписывает короткоживущее внутреннее утверждение для FastAPI. FastAPI
проверяет подпись, аудиторию, срок, уникальный ID и demo-флаг. Production-режим
не принимает demo-утверждения.

## Оперативный процесс

### Очередь инцидентов

Все события с `isAlarm=true` входят в очередь инцидентов. Нетревожные события
остаются в технологическом журнале, но не создают оперативную карточку.
Карточка объединяет наблюдение, канал, доступный объект, историю решений и
качество данных. Повторы источников не перезаписывают существующее решение.

Статусы карточки:

- `new`;
- `in_review`;
- `crew_dispatch`;
- `false_alarm`;
- `confirmed_incident`;
- `closed`.

Переход фиксируется отдельной неизменяемой записью. Исходное событие и
связанный прогноз остаются доступны после решения. Удаление решений через API
не предусматривается; корректировка оформляется новой записью с причиной и
ссылкой на исправляемое решение.

### Черновик заявки

Черновик формируется из выбранной карточки по детерминированному шаблону:
источник, объект или канал, категория, приоритет, рекомендуемый тип проверки,
срок, обоснование и автор. Черновик всегда имеет `provenance: "simulated"`,
пока используется demo help-desk. Отправка во внешнюю систему не имитируется
успешным ответом: интерфейс показывает только локальное создание и историю
изменений черновика.

### Аудит

В аудит записываются вход и выход из demo-сессии, отказы авторизации, просмотр
защищённых разделов, решения, исправления решений, создание и изменение
черновика, а также административные изменения профилей. Запись содержит
субъекта, действие, ресурс, время, безопасные детали и ссылку на предыдущий
хеш. Demo SQLite хранит цепочку между перезапусками. Промышленный контур требует
внешнего WORM-хранилища и закрепления головы цепочки.

## Схемная топология

API формирует GeoJSON `FeatureCollection` из подтверждённой иерархии объектов.
Оси коллекторов представлены `MultiLineString`. Координаты рассчитываются
детерминированно из положения узлов в дереве и не претендуют на географическую
точность. Каждая feature содержит:

- `objectId` и родительскую связь;
- фактический тип объекта;
- доступную область видимости;
- `geometrySource: "synthetic"`;
- `provenance: "derived"` для структуры и `simulated` для координат.

Экран называется «Схема объектов», а не «Карта Москвы», и содержит постоянное
предупреждение об условных координатах. Фильтры по типу объекта и доступной
области работают всегда. Фильтр риска включается только при наличии настоящего
валидированного ML-прогноза; сценарные карточки не подменяют его.

Один пикет отображается как 10 метров. Пересчёт расстояния выполняется в одном
доменном модуле и покрывается unit-тестами.

## API

Версионированные маршруты FastAPI:

- `GET /api/v1/situation` — наблюдения, качество и свежесть;
- `GET /api/v1/incidents` — очередь с серверной фильтрацией области;
- `GET /api/v1/incidents/{incident_id}` — карточка и история;
- `POST /api/v1/incidents/{incident_id}/decisions` — новое решение с
  обязательной причиной и `Idempotency-Key`;
- `GET /api/v1/service-request-drafts` — доступные черновики;
- `POST /api/v1/service-request-drafts` — детерминированный черновик;
- `PATCH /api/v1/service-request-drafts/{draft_id}` — допустимый переход;
- `GET /api/v1/topology` — схемный GeoJSON с серверным ABAC;
- `GET /api/v1/audit` — аудит для администратора с пагинацией.

Ошибки имеют стабильный код, русское безопасное сообщение и correlation ID.
Запись принимает ограниченный JSON, проходит rate limit до буферизации тела и
не возвращает внутренний traceback.

## Интерфейс

Strict flat Palantir-стиль из `SPEC.md` сохраняется. Новые экраны не используют
размытие, декоративное стекло, градиенты и большие скругления.

1. Header показывает режим, текущую роль, область, время обновления и состояние
   источника.
2. Провайдер данных обновляет снимок каждые 60 секунд, отменяет устаревший
   запрос и сохраняет last-known-good снимок при временной ошибке.
3. После возврата вкладки в активное состояние выполняется немедленная
   проверка. Одновременные запросы не запускаются.
4. Журнал показывает все наблюдения, а очередь инцидентов — тревожные события,
   решение, автора, происхождение и историю.
5. Карточка решения требует явной причины и подтверждения; UI не выполняет
   оптимистический переход до ответа сервера.
6. Раздел заявок показывает только черновики и их demo-происхождение.
7. Схема объектов предоставляет клавиатурную навигацию, текстовый список и
   табличную альтернативу визуализации.
8. Экспорты CSV/JSON содержат происхождение и время формирования.

## Хранение и миграции

Demo SQLite создаётся в игнорируемом каталоге `data/processed` с правами
текущего пользователя. Схема включает версии миграций, решения, черновики,
demo-сессии и аудит. SQL выполняется только параметризованными запросами.

Исходные наблюдения не копируются целиком в SQLite. Таблицы решений ссылаются
на канонический идентификатор и сохраняют минимальный неизменяемый снимок
контекста, необходимый для аудита. Повторная сборка локального снимка не удаляет
решения.

Интерфейс репозитория не использует SQLite-специфичные типы. Это сохраняет
переход к PostgreSQL 12+ отдельной инфраструктурной задачей.

## Безопасность

- demo-режим запрещён на публичном listener;
- секреты не имеют значений по умолчанию и не попадают в Git или ответы API;
- service token остаётся серверным и не используется как личность человека;
- все write-операции требуют пользовательской demo- или production-сессии;
- роли и области из тела, query и произвольных заголовков игнорируются;
- CSRF, Origin, Content-Type, размер тела и идемпотентность проверяются до
  изменения состояния;
- CSV/JSON-экспорт экранирует формульные префиксы;
- сырые пути, имена файлов и служебные метаданные не выдаются браузеру;
- системный аудит не содержит исходные показания, секреты и персональные поля;
- отключение demo-режима немедленно запрещает выдачу demo-сессий и запись.

## Проверка и критерии приёмки

### Контракты и данные

- старая схема каналов принимается с `objectId=null`;
- обновлённая схема принимает только существующие ID объектов;
- неизвестная или смешанная схема отклоняется;
- нетревожный sentinel исключается из аналитики, но сохраняется как факт;
- тревожный sentinel остаётся в оперативном журнале;
- 2021 год по умолчанию исключён из ML-наборов с явной причиной;
- один пикет всегда преобразуется в 10 метров.

### Идентичность и бизнес-процесс

- серверная матрица проверяет каждую роль и область видимости;
- районный диспетчер не видит чужой объект;
- центральный диспетчер видит все разрешённые карточки;
- техник ограничен назначенным комплексом;
- администратор не может принять бизнес-решение;
- повтор с одинаковым `Idempotency-Key` не создаёт второе решение;
- прогноз и событие остаются после решения;
- исправление создаёт новую аудируемую запись;
- черновик заявки сохраняется после перезапуска demo API.

### UI и эксплуатация

- polling выполняется с интервалом 60 секунд и не теряет last-known-good;
- stale/historical состояние визуально и программно доступно;
- simulated/observed происхождение видно без открытия модального окна;
- топология имеет доступную табличную альтернативу;
- production build, TypeScript strict, ESLint, Vitest и Pytest проходят;
- Ruff, Bandit, Semgrep, TruffleHog и dependency-аудит повторяются после
  реализации;
- проверяется запуск минимум 20 параллельных read-сессий и сериализация
  конфликтующих write-операций одного инцидента.

## Последовательность реализации

1. Контракт данных v2, правила качества и 60-секундное обновление.
2. Репозитории, SQLite-миграции и устойчивый аудит.
3. Demo-идентификация и точная RBAC/ABAC-модель.
4. Очередь тревог, решения и сохранение истории.
5. Черновики help-desk.
6. GeoJSON и экран схемной топологии.
7. Нагрузочные, accessibility и security-проверки.
8. Обновление `DECISIONS.md`, `TZ_COMPLIANCE.md`, руководств запуска и
   демонстрационного сценария по фактическому результату.

## Явные границы результата

Контур не заявляет наличие обученной ML-модели, настоящих координат, реального
